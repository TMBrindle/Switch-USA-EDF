# Regional Wind Growth Caps & Zonal LMP Output

**Branch:** `tom/regional-wind-caps` (merged via PR #7 into `edf-baseline`)
**Completed:** 2026-07-17

---

## Overview

This PR adds two independent pieces of functionality, plus three bug fixes found
while validating them:

1. **Regional (per-transreg) wind growth caps** — disaggregates the existing
   national `MaxCapTag_WindGrowth` limit into nine per-transreg caps, so onshore
   wind build-out is constrained regionally as well as nationally.
2. **`write_zonal_lmp` study module** — a new post-solve output module that
   derives zonal LMPs ($/MWh) from the model's internal energy-balance duals.
3. **Bug fixes:**
   - `write_zonal_lmp.py` sort crash on mixed int/str timepoint IDs.
   - `adjust/increase_timepoint_duration.py` path-lookup bug on foresight builds.
   - `pg_to_switch.py` `cap_req_files()` could emit a `max_cap_mw` below
     already-committed predetermined capacity, silently making any `MaxCapTag_*`
     program infeasible.

These are independent features — you can use either one without the other.

---

## Part 1 — Regional Wind Growth Caps

### What it does

The existing national wind cap (`MaxCapTag_WindGrowth`, 14,490 MW/yr of new
onshore wind, defined in `make_emission_policies.py`) still applies unchanged.
This PR adds nine **additional, region-specific** caps on top of it:

```
MaxCapTag_WindGrowth_CAISO
MaxCapTag_WindGrowth_ERCOT
MaxCapTag_WindGrowth_ISONE
MaxCapTag_WindGrowth_MISO
MaxCapTag_WindGrowth_NYISO
MaxCapTag_WindGrowth_NorthernGrid
MaxCapTag_WindGrowth_PJM
MaxCapTag_WindGrowth_SPP
MaxCapTag_WindGrowth_WestConnect
```

Each onshore wind generator is tagged with **both** the national tag and its
transreg's regional tag (`regional_resource_tags.yml`), so the model must
satisfy the tighter of the two constraints in every zone/period. There is no
regional cap for `SERTP` or `FRCC` — those transregs have no LBNL interconnection
queue coverage (see below), so only the national cap constrains them.

### Three-tier methodology (by model year)

| Period | Method | Basis |
|---|---|---|
| ≤ 2028 | **Pipeline** | baseline + (LBNL IA-executed MW + 25% × non-IA active MW) from the interconnection queue |
| 2029–2030 | **Regional historical share** | baseline + (transreg's share of national 14,490 MW/yr, per 10-yr EIA 860M deployment history) |
| ≥ 2031 | **None** | only the national cap applies |

- **Baseline** = existing, non-retiring onshore wind capacity in the transreg as of
  `last_hist_year` (2024), from EIA 860M.
- **Pipeline method (≤2028)** grounds the near-term cap in signed interconnection
  agreements rather than a historical trend, since near-term build-out is
  determined by what's already in the queue, not by growth rates. Only ISONE,
  NYISO, and PJM have LBNL queue coverage; other transregs skip the regional cap
  for this window (national cap still applies).
- **Regional method (2029–2030)** is intentionally slightly looser than the
  pipeline cap — it reflects pipeline maturation as more projects reach
  interconnection agreements.
- **≥2031**: regional supply-chain/siting constraints are assumed to ease over a
  decade-plus horizon, and 10-year-old deployment shares stop being predictive,
  so the regional disaggregation is dropped and only the national limit remains.

Caps are **cumulative and monotonically non-decreasing** by period (2028 cap ≤
2030 cap ≤ national cap thereafter) — this is enforced by both
`make_emission_policies.py` (baseline + cumulative growth) and the
predetermined/prior-year floors described below.

### Preparing inputs

The wind caps are generated as part of the normal `make_emission_policies.py` →
`pg_to_switch.py` pipeline. Nothing extra is required at the `pg_to_switch.py`
call site — regional tags flow through `regional_resource_tags.yml` and
`scenario_management.yml` like any other `MaxCapReq` tag.

**One extra input file is required**, not generated by this repo:

```
docs/analysis/RGGI/lbnl_queue_by_state.csv
```

Generate it by running `docs/analysis/RGGI/lbnl_queue_vs_model.py` against
`LBNL_Ix_Queue_Data_File_thru2025.xlsx` before running `make_emission_policies.py`.
**If this file is missing, `make_emission_policies.py` raises
`FileNotFoundError` and stops** — the pipeline/2028-cap tier cannot be computed
without it. If you only care about years ≥2029, you'd still need to either
provide this file or comment out the regional-cap block (see "Turning it off"
below).

### Build order

1. Run `docs/analysis/RGGI/lbnl_queue_vs_model.py` (produces
   `lbnl_queue_by_state.csv`) if it doesn't already exist or the source LBNL
   workbook has been updated.
2. Run `make_emission_policies.py` as usual — this writes both the national
   caps and the new regional caps to `scenario_management.yml` and
   `regional_resource_tags.yml`, and registers the new tag names in
   `model_definition.yml` / `resource_tags.yml`.
3. Run `pg_to_switch.py` as usual to build/rebuild case input folders. The
   `max_cap_generators.csv` / `max_cap_requirements.csv` files for each case
   will include the regional tags automatically, with the predetermined-capacity
   floor applied (see Bug Fix 3 below).

### Updating caps for *existing* case folders without a full rebuild

If you've already built input folders and only want to refresh the wind-cap
files (e.g. after re-running `make_emission_policies.py` with updated LBNL/EIA
data), use:

```
python pg/update_max_cap_files.py
```

This regenerates `max_cap_generators.csv` and `max_cap_requirements.csv` only,
for the hardcoded case list in that script:

```python
YEARS = [2028, 2030, 2035]
CASES = ["s4x1_edf_med", "s4x1_icf", "s4x5_edf_med", "s4x5_icf",
         "s20x1_edf_med", "s20x1_icf"]
```

**If your case names or years differ, edit these two lists at the top of the
script before running it** — it silently skips (and reports as "Skipped") any
`year/case` combination it can't find under `switch/in/`. It does not touch
non-`MaxCapTag_WindGrowth_*` entries in those files, so it's safe to run
repeatedly.

This script also applies both floors described below (predetermined capacity,
and prior-model-year cap monotonicity) independently of the `pg_to_switch.py`
floor, since it doesn't go through `cap_req_files()`.

### Turning it off

- **To drop only the regional disaggregation** (keep the national wind cap):
  comment out or delete the block in `make_emission_policies.py` starting at
  `# Regional wind growth limits: disaggregate MaxCapTag_WindGrowth...`
  (search for `NON_IA_FRACTION`), then re-run `make_emission_policies.py` and
  `pg_to_switch.py`. This also avoids the `lbnl_queue_by_state.csv` dependency.
- **To drop all wind growth constraints** (national + regional): also remove
  the `MaxCapTag_WindGrowth` entry from `max_growth_limits` near the top of
  `make_emission_policies.py`.
- Because tags are cleared and rewritten each run
  (`delete_yaml_keys(... "MaxCapTag_WindGrowth_*")`), simply not running the
  regional block is sufficient — no manual cleanup of `regional_resource_tags.yml`
  is needed, the next `make_emission_policies.py` run will remove stale entries.
- If you've already built case folders with the regional tags and want to strip
  them back out without re-running the whole pipeline, you'd need to manually
  remove `MaxCapTag_WindGrowth_*` rows from `max_cap_generators.csv` /
  `max_cap_requirements.csv` in each case folder — `update_max_cap_files.py` only
  adds/refreshes these entries, it doesn't remove the regional tags if the
  source YAMLs no longer define them for a transreg it previously covered on the
  first pass. Easiest path is a full rebuild if you're turning it off.

### Caveats & things to watch for

- **SERTP and FRCC have no regional cap** — only the national cap constrains
  wind build-out there, for any period. This is intentional (no LBNL queue
  coverage) but can look inconsistent if you're comparing regional cap
  tightness across transregs.
- **The `BA_TO_TRANSREG` mapping is hand-maintained** in
  `make_emission_policies.py`. If EIA 860M balancing-authority codes change or a
  new BA appears, wind capacity from an unmapped BA silently drops out of the
  regional baseline/share calculation (it still counts toward the *national*
  cap via the original `max_growth_limits` query, since that doesn't use
  `BA_TO_TRANSREG`).
- **`ONSHORE_WIND_TECH_KEYS` is a substring-prefix match** against `gen_tech`
  (`tech.startswith(key)`), matching PowerGenome ATB names like
  `LandbasedWind_Class3_Moderate`. If a new wind technology naming convention is
  introduced upstream (a PowerGenome/ATB version bump, e.g.), it may not match
  any key and will fall outside all `MaxCapTag_WindGrowth_*` programs
  (offshore wind is intentionally excluded — it's a different technology
  category with its own `MinCapTag_` OSW policy).
- **Two floors can override the computed cap**, both intentional but easy to
  forget when interpreting a scenario's binding constraint:
  1. **Predetermined-capacity floor** — a cap can never be set below the sum of
     already-committed (`gen_build_predetermined.csv`) capacity for a program's
     tagged generators (see Bug Fix 3). If you see a `max_cap_mw` that looks
     larger than what `make_emission_policies.py` computed, this is why — check
     the `WARNING cap_req_files:` messages printed during `pg_to_switch.py`, or
     the `cap raised X -> Y MW` messages from `update_max_cap_files.py`.
  2. **Prior-model-year floor** (in `update_max_cap_files.py` only, not in
     `pg_to_switch.py`'s `cap_req_files()`): each year's effective cap is also
     floored at the *previous* model year's effective (post-floor) cap, so caps
     never shrink between periods within one call of the script. Note this
     monotonicity is only enforced within a single `update_max_cap_files.py`
     run — if you regenerate `scenario_management.yml` with genuinely
     decreasing caps across periods and go through `pg_to_switch.py` directly
     (not `update_max_cap_files.py`), the per-period predetermined floor still
     applies but this cross-period ratchet does not.
- **This is a disaggregation of an existing national constraint, not a new
  independent one** — if you're debugging an infeasibility or an unexpectedly
  tight wind result, check both the national and the region's tag in
  `max_cap_requirements.csv` for the binding one.

## Part 2 — `write_zonal_lmp` Study Module

### What it does

`switch/study_modules/write_zonal_lmp.py` is a post-solve module that derives
zonal locational marginal prices from the model's internal
`Distributed_Energy_Balance[z, t]` constraint dual (the shadow price of serving
one more MW at zone `z`, timepoint `t`), dividing by `tp_weight_in_year[t]` to
convert from a per-timepoint $/MW shadow price to a $/MWh price.

It writes two files to the run's `outputs_dir` after each solve:

| File | Contents |
|---|---|
| `zonal_lmp.csv` | One row per zone × timepoint: `load_zone, timepoint, period, lmp_real_per_mwh, load_mw, tp_weight_hr, is_extreme_day` |
| `zonal_lmp_annual.csv` | Load-weighted annual average LMP per zone × period, **excluding extreme-day timepoints**: `load_zone, period, lmp_annual_avg_real_per_mwh, load_weighted_twh` |

Timepoints are flagged `is_extreme_day` (and excluded from the annual average,
though still written to the per-timepoint file) if their timeseries'
`ts_scale_to_period` is below a threshold — this catches PRM-only timepoints
(scale = 0) and extreme-day timeseries (scale ≈ 0.43), since their prices
reflect scarcity events rather than typical market conditions and would badly
skew an annual average.

### Enabling it

Add the module to `switch/modules.txt`, after `study_modules.write_dual_costs`
(or any other module that already sets up the `dual` Suffix):

```
study_modules.write_dual_costs
study_modules.write_zonal_lmp
```

It requires two things to already be present on the model, and **silently
no-ops with a printed message rather than erroring** if either is missing:
- `switch_model.transmission.local_td` loaded (for `Distributed_Energy_Balance`)
  — already the case in this repo's standard `modules.txt`.
- A `dual` Suffix on the model. `write_dual_costs.py` (already registered)
  creates `m.dual = Suffix(direction=Suffix.IMPORT)` if it doesn't already
  exist, so as long as `write_zonal_lmp` loads after it (or after any other
  module/solve option that sets up duals), this is satisfied automatically. If
  you remove `write_dual_costs` from `modules.txt`, you'll need another way to
  attach the dual suffix or `write_zonal_lmp` will skip silently.

### Optional CLI flag

```
--lmp-extreme-day-threshold SCALE   (default: 2.0)
```

Timeseries with `ts_scale_to_period` below this value are excluded from the
annual average. The default (2.0) is chosen to catch scale=0 (PRM-only) and
scale≈0.43 (extreme day) timeseries while including regular days (scale 100+).
Add it to `options.txt` or a per-run flag if you need a different cutoff for a
non-standard time-sampling scheme.

### Turning it off

Remove (or comment out) the `study_modules.write_zonal_lmp` line from
`modules.txt`. No other cleanup needed — it produces no input files and has no
effect on the optimization (it's a pure post-solve reporting module).

### Caveats & things to watch for

- **These are shadow prices from an LP relaxation of a MIP**, not a "true"
  market-clearing price in the FERC/ISO sense — with unit commitment binary
  variables fixed at their solved values, duals reflect the marginal cost of
  the *relaxed* problem at the optimum, which can differ from real-world LMPs
  around commitment/startup decision points.
- **Requires the solver to actually return duals for a MIP.** Some solvers only
  report duals for the LP relaxation, or only after fixing integers and
  re-solving as an LP. If `m.dual` exists but is empty for the relevant
  constraints, `dual.get(constr, 0.0)` defaults to `0.0` silently — a run full
  of `lmp_real_per_mwh == 0` for a zone likely means duals weren't populated,
  not that the zone truly has a zero marginal price.
- **`zonal_lmp_annual.csv` excludes extreme days from the load-weighted
  average** — don't compare it directly to metrics that include those hours
  (e.g., a naive average over `zonal_lmp.csv`). The two files answer different
  questions: `zonal_lmp.csv` is the full picture, `zonal_lmp_annual.csv` is a
  "typical year" price signal.
- **The sort-crash fix** (Bug Fix 1, below) means older cached results run
  before this PR under mixed int/str timepoint IDs may have been silently
  incomplete/crashed rather than producing a valid file — regenerate outputs
  for any run made against a mixed-ID timepoint set before this fix.

## Part 3 — Bug Fixes (from feature-validation testing)

These aren't features to opt into — they fix latent bugs found while testing
Parts 1 and 2 above. No action needed beyond pulling the updated code.

### Fix 1 — `write_zonal_lmp.py` sort crash

`sorted(m.TIMEPOINTS)` and `sorted(m.LOAD_ZONES)` had no `key=`, which crashes
with a `TypeError` if timepoint or zone IDs are a mix of `int` and `str` (can
happen depending on how input CSVs are read/typed). Fixed by sorting with
`key=str`.

### Fix 2 — `increase_timepoint_duration.py` path lookup on foresight builds

`get_tp_duration_hours()` previously assumed a fixed path depth
(`.../switch/in/{year}/{case_id}`) to locate
`pg/extra_inputs/scenario_inputs.csv`, and required a numeric `year` directory
name. This broke on:
- Foresight/multi-period builds (`.../switch/in/foresight/{case_id}`, no single
  `{year}` directory).
- Any other nonstandard inputs-dir layout (e.g. `switch/in_tests/...`).

It now searches upward from `in_dir` (up to 8 parent levels) for
`pg/extra_inputs/scenario_inputs.csv`, and if no numeric year can be parsed
from the parent directory name, matches rows in `scenario_inputs.csv` by
`case_id` alone — **requiring all matched rows to agree on
`tp_duration_hours`** (raises `ValueError` if they don't, since one built
inputs directory can only use a single timepoint resolution across all
periods).

**Watch for:** if you have a foresight case where different periods were meant
to use different timepoint resolutions, this will now raise an error instead
of silently picking one value — that's correct behavior (a single built inputs
dir can't mix resolutions), but it means such a setup needs to be split into
separate builds.

### Fix 3 — `pg_to_switch.py` predetermined-capacity floor on `MaxCapTag_*` caps

`cap_req_files()` (the function that writes `max_cap_requirements.csv` for
every `MaxCapTag_*`/`MinCapTag_*` program, not just the wind caps) could
previously emit a `max_cap_mw` below the already-committed
(`gen_build_predetermined.csv`) capacity of that program's tagged generators.
Since predetermined builds are fixed (can't be "unbuilt" by the optimizer),
this made the model **unconditionally infeasible** the moment such a case was
solved — regardless of any other input or scenario choice.

This was previously only guarded against by remembering to run
`pg/update_max_cap_files.py` after the fact. Now, every `pg_to_switch.py` run
automatically floors `max_cap_mw` at the summed predetermined capacity for a
program's tagged generators, and prints a warning when it does so:

```
WARNING cap_req_files: <PROGRAM> (<PERIOD>) max_cap_mw <X> is below predetermined
capacity <Y>; raising cap to the predetermined floor.
```

**This applies to every `MaxCapTag_*`/`MinCapTag_*` program**, not just the new
regional wind caps — if you're debugging why a cap in `max_cap_requirements.csv`
doesn't match what you expect from `scenario_management.yml`, check for this
warning in the `pg_to_switch.py` log output first.

Note this floor is **per-period independently** — unlike
`update_max_cap_files.py`'s prior-year ratchet (see Part 1), `pg_to_switch.py`
does not enforce that a later period's cap stays ≥ an earlier period's cap,
only that each period individually clears its own predetermined floor.

## Quick reference: what to run, in what order

```
# 1. (regional wind caps only, if LBNL data changed)
python docs/analysis/RGGI/lbnl_queue_vs_model.py

# 2. Regenerate policy caps (national + regional wind, ESR, OSW, etc.)
python make_emission_policies.py

# 3. Build/rebuild Switch input case folders
python pg_to_switch.py <settings...>

# 4a. If you only touched wind-cap inputs and don't want a full pg_to_switch
#     rerun for already-built cases:
python pg/update_max_cap_files.py

# 4b. Enable zonal LMP output (edit switch/modules.txt once, no per-run step)

# 5. Solve as usual
```
